html-modules Routing with mport

Routing with mport v2

A Router answers one question: where does this specifier live? html-modules keeps the order (import map, then router, then the host) and the non-package routes: static aliases, HTML-module paths, app schemes. Packages go to mport v2 through fromMport(createRouter(...)): version ranges, npm:/jsr:, mirrors, strategies, health, traces and lockfiles. Everything here runs offline: two local "mirrors" serve the packages, a local registry answers version lookups, and outages and latency are simulated.

A chain, traced

importMapRouter(pins)→basicRouter(@internal/*)→toRouter(partials)→fromMport(fallback(down, race(primary, backup)))
const packages = createRouter({
  '*': fallback(mirror('down'), race(mirror('primary'), mirror('backup'))),
}, { fetch: localRegistry, probe: simulatedProbe });   // the probe imports the module
const loader = createLoader({ router: chainRouters(pins, internal, partials, fromMport(packages)) });

Each specifier is loaded through the chain. "Routers asked" shows which routers were asked and which answered; the mport trace shows the registry lookup and every probe. importModule calls are counted: mport's probe already evaluated the module, so the loader reuses it. Run it a few times: the race winner is whichever mirror gets the short simulated latency (the other would take over 2 s and is aborted), and after three failures the "down" mirror's circuit opens and it is skipped.

    Strategies

    The same request, greet@^1, through three strategy trees. Simulated network: primary is down (it fails after 5 ms), backup answers in 30 ms, slow (another copy of backup) would take 2 s.

      Health and the circuit breaker

      createRouter(routes, { circuitBreaker: { failures: 2, reset: '30s' } }) with fallback(primary, backup) and primary down. After two failures in a row the circuit opens and primary is skipped without a request. A second router created with { health: first.health } shares that state.

        Lockfile pinning and integrity

        A first router resolves ranges through the registry and records version, build and (with verified()) an SRI hash. A second router gets that lockfile: it asks the registry nothing, skips a provider that serves a different build, and rejects a mirror whose bytes do not match the pinned hash.

        const first = createRouter({ '*': fallback(verified(mirror('primary')), verified(mirror('backup'))) }, { fetch });
const { importMap, lock } = await first.build(['greet@^1', 'jsr:@demo/scoped@^2']);
const pinned = createRouter({ '*': fallback(transformCdn, verified(mirror('backup')), verified(mirror('primary'))) }, { fetch, lock });
