html-modules Settings

Settings

Two optional elements set defaults for one document. <html-import-settings> configures the imports of the page (or module) it appears in: delimiter, base, conflict, load and errors. <html-module-settings>, inside an HTML module, configures that module's component exports: shadow and delegates-focus. Settings are lexical: they never leak from a page into the modules it imports, or back out. Lazy loading has its own page.

One element for the whole page, and the precedence

<html-import-settings delimiter="-"></html-import-settings>     <!-- first: before any <html-import> -->

<html-import src="./components/ui.html" as="ui"></html-import>                   <!-- <ui-card>, <ui-badge>, … -->
<html-import src="./components/ui.html" as="classic" delimiter="--"></html-import> <!-- the attribute wins: <classic--card> -->
<ui-card>The page's delimiter="-". ui-badge <classic--card>Its own delimiter="--" overrides the page. classic--badge

Each import's el.settings, and where each value came from

Precedence, for each option: the <html-import> attribute, then the document's <html-import-settings>, then the createHTMLModules({ … }) options of the instance, then the built-in defaults (--, error, eager, event). base is document-level only.

    base: pick a library version for the whole document

    base is like <base href>, but only for HTML imports. It is resolved against the document's own URL and changes how every <html-import src> in that document resolves, and nothing else: links, images and the programmatic API are unaffected. The frame below imports src="./kit.html"; switching base switches it between vendor/ui@1/ and vendor/ui@2/. Version 2 re-exports a chip from ./extras.html, which resolves against the module's own URL. 

    <html-import-settings base="../vendor/ui@1/"></html-import-settings>
<html-import src="./kit.html" as="ui"></html-import>
    settings/base-v1.html

      conflict: a compiled copy and a runtime copy on one page

      Each frame first loads compiled/icons.register.js, a compiled build of icons.html that registers <reg--star>, <reg--heart>, … on import. Then it imports the HTML source of the same module under the same namespace. Those are different definitions of the same tags. With conflict="error" (the default) that is an error. With conflict="reuse" the import keeps the existing definitions and records them as reused.

      conflict="reuse": settings/conflict-reuse.html

      conflict="error": settings/conflict-error.html

        errors="throw": failures reach window.onerror too

        By default a failure is an error event and a rejected el.ready, which is quiet unless you listen. With errors="throw" it is also passed to reportError(), so it shows in the console and in window.onerror, like an uncaught exception. Handy during development. The frame captures what window.onerror receives (and marks it handled, so the console stays clean); one import opts back out with errors="event".

          Scope is lexical

          This page's delimiter="-" applies to this page's imports only. rating.html has no settings: its template was written with <icon--star>, and it still gets exactly that. stamp.html has its own <html-import-settings delimiter="-">, which applies inside it (<glyph-heart>) and nowhere else.

            <html-module-settings>: defaults for a module's exports
            
      
            
        Inside an HTML module, <html-module-settings shadow="closed" delegates-focus> makes every component export default to a
        closed shadow root that delegates focus. An export's own shadow and delegates-focus attributes override it
        (delegates-focus="false" turns a default off). The defaults are part of each definition, so the compiler produces the same thing.

              Placement rules
              
      
              
        A document has at most one <html-import-settings>, and it must come before every <html-import>. A late or
        second one is an error event on that element and is ignored: it never changes imports that have already started. Unknown
        attributes and bad values are errors that name the valid values; bad values also fail the document's imports. Inside a module, the same
        rules are SyntaxErrors when the module loads (see Errors).
